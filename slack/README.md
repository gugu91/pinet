# @pinet/slack

A separate Slack transport for `@pinet/chat`. Chat itself has no Slack dependency. The adapter receives human messages over authenticated Slack Socket Mode, posts through the Slack Web API, and calls Chat's authenticated HTTP API.

Set `PINET_SLACK_ENABLED=true`, `SLACK_APP_TOKEN`, `SLACK_BOT_TOKEN`, `SLACK_BOT_USER_ID`, `PINET_CHAT_URL`, and a dedicated bridge-agent `PINET_SLACK_CHAT_TOKEN`. The adapter is default-off: without explicit enablement it does not open the mapping database or acquire its process lease. Use `PINET_SLACK_DB` to move the SQLite mapping database. The lease is acquired lazily by an active bridge, atomically serializes concurrent starts, and includes process-generation identity so PID reuse can be reclaimed safely. Then explicitly map channels with `pinet_slack` action `bind_channel`. Thread mappings are created only after a successful root relay; queued replies wait durably for their root rather than being sent into the wrong thread.

The adapter prefixes inbound text with the verified Socket Mode event's Slack user ID. Configure Slack-user-to-agent mention mappings when registering programmatically. Bot events, the adapter's own user, known Slack timestamps, and known Chat IDs are suppressed to prevent loops. Tokens are authorization headers, never query parameters or logs. Socket Mode reconnects with bounded backoff. Callbacks are scoped to their source socket generation: stale sockets cannot enqueue or acknowledge envelopes, close the current socket, or schedule another reconnect.

There is no Events API HTTP receiver. Outbound Chat delivery uses durable per-channel cursors because Chat's portable notification path is HTTP in this version. Since Slack does not provide a supported idempotency key for `chat.postMessage`, a failure after posting begins is recorded as ambiguous and is not blindly retried. Inspect `outbound_ambiguous`, reconcile the Slack channel, then explicitly authorize `outbound_retry` when appropriate. No live Slack send or connection is made in tests.
